# EIC sizing calculator

Open `index.html` in a browser, or serve this directory with any static HTTP server. No framework, build, account, deployment or cloud provisioning is required. Keep `azure-sizing.js`, `azure-view.js` and `terraform-export.js` beside the HTML file. SAP fonts are fetched externally when available; system fonts are the fallback.

Enter synchronous / asynchronous throughput, then open **Azure Mapping**. Select a planning region, node SKU, Solace tier and availability model. Edit the planning assumptions to match your deployment. The result shows aggregate capacity constraints, individual-pod fit, normal/survivor allocation and an **unpriced** resource bill of materials. Invalid assumptions block estimates; blank throughput means zero. Negative throughput retains workbook behavior but blocks Azure sizing.

## Workbook compatibility

The original `eic-calc` engine in `index.html` is unchanged. The Azure model is separate and consumes its results. In particular, synchronous sizes retain 3096 / 4192 KB, async CPU-time total excludes the final 5 MB row, and ROUNDUP retains the existing 15-significant-digit handling. Guide tables have not replaced workbook formulas. Focused regression tests are not a claim of exhaustive Excel equivalence; third-party formula engines can differ at floating-point integer boundaries.

## Azure estimation methodology

- **Catalog:** necessary factual CPU/memory/SAPS values from SAP Note 1928533 v199 (2026-11-04), pp.4/5/8; version `2026-11-04-note1928533-v199`. SAPS, not ASAPS. General SAP VM ratings are capacity references, not AKS/EIC certification. Dsv6/Esv6/Dsv5 specifications were cross-checked against Microsoft Learn on 2026-11-13.
- **Source floors:** SAP Note 3247839 v96 (2026-11-03), p.2: aggregate non-HA 10 CPU / 32 GiB / 101 GiB persistent; HA 20 / 64 / 204. Pod planning floors are 40 / 90 (upper end of the source's approximate HA range). These include EIC components, not extra resources to add to them.
- **Component model:** worker pods are the greater of SAPS-derived count, memory-derived count, and minimum 1 non-HA / 2 HA. Defaults assume 1,400 SAPS, 1 CPU, 4 GiB per worker pod. Policy uses 1,400 SAPS, 1 CPU, 1 GiB per assumed pod and the same replica minimum. These are editable **application assumptions**, not actual deployment requests. Original workbook GB numbers are conservatively budgeted as GiB. Separate other-component totals and largest-other-pod assumptions must be reconciled with real manifests.
- **Broker:** source p.2 tier CPU/memory limits, not verified requests. HA has three equal-limit pods, two full-size data disks and a 3 GiB monitor disk. Tier 250 HA is 6 CPU / 19.5 GiB / 203 GiB. Broker replaces the workbook's fixed broker within this separate model; no extra workbook broker SAPS is added.
- **Demand:** CPU/memory/pods = maximum of source baseline and modelled components, not their sum. SAPS = max(16,423 non-HA / 32,846 HA, workbook worker + policy + editable other-component SAPS). The other-component allowance defaults to 8,400 from guide snapshot 2026-10-13 pp.7-8, but composition and reconciliation are ambiguous. Replace this proxy with a cluster-only allowance excluding external DB/cache; within this model it covers broker, without adding workbook broker SAPS again. This is an explicit app rule, **not SAP-approved accounting**; broker tier changes have no verified SAPS conversion.
- **Allocation:** default 15% reserve reduces each node's CPU/memory/SAPS; 20% demand headroom is applied once to each aggregate constraint. Node count must meet the maximum of SAPS, CPU, memory, pod slots and worker ephemeral capacity constraints after the chosen failure. Largest assumed pod SAPS/CPU/memory/10 GiB ephemeral must fit one usable node; aggregate arithmetic is not bin packing.
- **Failure models:** none; any one node; or largest zone of three balanced zones (survivors = N - ceil(N/3)). HA conservatively retains full configured aggregate demand and at least three surviving nodes for three separate assumed broker placements. No inferred HA from a percentage. Guide p.26's 30% is **not** stacked onto doubled note floors. Real quorum, anti-affinity, PDBs, topology, rescheduling and storage recovery still need validation.
- **Storage:** core persistent allowance = max(note floor, broker volumes + workbook policy disk), **including** broker, not an additional volume. Optional 20 GiB Prometheus and 51 GiB shared storage are separate. Broker: expandable block/XFS, >=1,000 IOPS per disk, no NFS. Shared: Azure Files SMB/RWX with Immediate binding. Source p.4 requires >=80 GB OS disks; catalog series' p.4/5/8 base VHD minimum is 128 GB. BOM assumes managed OS disks and 60 GiB usable OS-backed ephemeral space per node; selected SKUs have no local temp disk. Validate the AKS image, disk performance, actual free space and 10 GiB default worker stream-cache limit. Prefer ephemeral OS only on a compatible SKU/image.
- **External services:** note p.3 supports PostgreSQL 15 (minimum 1 CPU / 2 GiB, PostgreSQL auth only) and Azure Managed Redis (minimum 1 CPU / 1 GiB, access keys only, enterprise clustering recommended, EIC mode Standalone). These source snapshot minima are **not managed SKU recommendations**. DB/cache resources are excluded from AKS; throughput, retention, payload/artifact/policy counts, capacity, backups and HA must be gathered before selecting managed tiers.

The UI includes links and page references. SAP documents may require authorization. Restricted PDFs/workbooks are deliberately not included. Snapshot facts can become stale; recheck current SAP support, Kubernetes versions, Azure regional SKU availability, quota, zones, networking/IPs, actual allocatable resources and scheduling before deployment. No pricing, quota, regional availability or managed-service SAPS is fabricated. Estimates above 10,000 nodes are blocked rather than presented as deployable.

## Save / import / export

Controls persist under the original browser storage key using schema version 2. Export retains legacy `inputs` / `results` fields and adds `azure.scenario`, computed results, catalog version and source metadata. Legacy raw inputs and original exports still import with default Azure assumptions. Imports validate before changing current state, ignore imported results, and recompute locally. Invalid imports/storage and failed persistence are visible; invalid edits are not saved and cannot be exported. Import files are limited to 1 MiB.

**Reset inputs** resets both workbook inputs and the Azure scenario. Persistence is browser/origin-specific; use JSON exports for transfer.

## Deploy card / Terraform export

Below the Azure methodology, select **Preview variables.tf**, review the generated file and compatibility warnings, then **Confirm and download variables.tf**. Cancel or Escape closes the dialog without downloading. The downloaded bytes are exactly the preview; changing calculator inputs invalidates an open preview. Invalid/blocked Azure estimates cannot be exported. This is a local file export, **not an Azure deployment**.

The exporter follows the names, types and validations of [the accelerator PaaS variable contract](https://github.com/Azure/sap-edge-integration-cell-on-azure-accelerator/blob/cc90ea65cdcd3cff4006ef0611f1bb2ba1a95a7e/production-ready/azure-paas/variables.tf), pinned to commit `cc90ea65cdcd3cff4006ef0611f1bb2ba1a95a7e`. The derived variable declarations include the upstream Microsoft MIT notice in every download. No runtime network fetch is needed.

Defaults map the chosen region and HA intent to `location` / `postgres_ha_enabled`; `postgres_version` is set to **15** per the SAP snapshot, rather than upstream's 16. PostgreSQL/cache SKU, storage, capacity and zone settings remain **required** because the calculator has not sized or verified them. Supply resource names, subnet IDs and conditional DNS/Key Vault IDs separately. Retained defaults (such as backup retention) are upstream examples, not sizing recommendations.

**Compatibility limit:** the linked PaaS module has no AKS node, maxPods, Solace, PVC or replica variables. The complete current mapping, assumptions and sources are therefore included as **reference comments**, not invented executable settings. Its `main.tf` actually provisions `azurerm_redis_cache` (Azure Cache for Redis), despite its Managed Redis wording; exporting variables cannot migrate it to the mapping's preferred Azure Managed Redis. Review/adapt the accelerator before applying.

Replace `variables.tf` inside the accelerator's `production-ready/azure-paas` directory. Do not use this declaration file as `terraform.tfvars`. Existing `.tfvars`, `TF_VAR_*` environment values and CLI arguments override variable defaults; remove conflicting sample overrides (notably PostgreSQL 16). Actual deployment and validation of the accelerator are outside the export feature.

## Checks

Run `node --test calculator.test.cjs` (Node.js 18+). No packages are required. Tests cover workbook quirks/rounding, resource floors, HA/broker accounting, failure survivors, bottlenecks, individual pod fit, invalid/huge values, state compatibility, Terraform variable schema/defaults/reference-only settings and non-mutation.
